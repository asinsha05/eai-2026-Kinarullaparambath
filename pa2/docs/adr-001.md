# ADR-001 — Durable delivery for order messages via RabbitMQ
Status: accepted Date: 2026-09-21
Context The producer receives orders over HTTP and places them onto RabbitMQ for later processing by the warehouse service. Because the warehouse service is external, unreliable, and outside our control, the API cannot wait for it before responding to the client. In practice, this means the broker becomes the boundary between a successful 202 Accepted response and potential data loss. While testing failure scenarios, four reliability concerns became apparent.

Queue Durability Initially, the queue was created without durability enabled. This worked normally during development but exposed a problem when RabbitMQ was restarted: the queue itself disappeared along with any messages it contained. A non-durable queue behaves identically to a durable one under normal operation, which makes the issue easy to overlook until the broker restarts. To prevent orders from being lost during broker restarts, the queue must be declared as durable.

Meaning of a 202 Response Testing publisher confirms demonstrated that a 202 Accepted response can be misleading if it is sent too early. In a fire-and-forget implementation, the API publishes the message and immediately responds to the client. If RabbitMQ becomes unavailable or is restarted before persisting the message, the client has already been told the request was accepted even though the order was never safely stored. To ensure the response reflects reality, the API should only return 202 after RabbitMQ confirms receipt of the message.

Acknowledgement Timing The consumer writes received messages to received.jsonl and acknowledges them afterward. If acknowledgements occur before writing and the consumer crashes in the small window between those two operations, RabbitMQ assumes the message has been successfully processed and permanently removes it from the queue. Since the write never completed, the order is lost without any record of its existence. Writing first and acknowledging second avoids this failure mode and preserves at-least-once delivery semantics.

Correlation ID Propagation Clients use correlation IDs to trace requests through the system. For tracing to be reliable, the same correlation ID must be preserved across every stage of the pipeline:

HTTP Header -> AMQP Property -> JSONL Record The value should be transported as message metadata rather than embedded in the payload itself. This keeps tracing concerns separate from application data and allows consumers to access the ID without parsing the message body.



##Decision

Durable Queues and Consumer Configuration connectProducerChannel creates a RabbitMQ ConfirmChannel and declares the queue using: assertQueue(queueName, { durable: true }) connectConsumerChannel declares the same queue with matching durability settings and configures: channel.prefetch(1) This limits the consumer to one unacknowledged message at a time and prevents it from receiving more work than it can safely process.

Confirmed Publishing publishMessage supports two publishing modes. The default mode (confirmed) sends persistent messages using a confirm channel and waits for RabbitMQ to acknowledge receipt before returning control to the HTTP handler. As a result, the client receives 202 Accepted only after the broker has confirmed the message. The alternative fire-and-forget mode publishes without persistence or publisher confirms and returns immediately. This mode demonstrates how messages can be lost even when the client has already received a successful response.

Manual Acknowledgements When a message is received, handleMessage:

Reads the correlation ID from the AMQP message properties. Writes a record containing the payload, correlation ID, and timestamp to received.jsonl. Acknowledges the message. The write operation occurs before the acknowledgement, ensuring that a message is not removed from the queue until a durable record has been created.

Correlation ID Handling The correlation ID is stored exclusively in the AMQP message properties. The producer sets the value using: { correlationId: options.correlationId } and the consumer retrieves it from: msg.properties.correlationId The correlation ID is never included in the message body, maintaining a clean separation between business data and tracing metadata.

##Alternatives considered

Acknowledge Before Writing This approach was rejected because a consumer crash after acknowledgement but before persistence would result in permanent message loss. The broker would consider the message successfully processed even though no durable record existed. For the same reason, asynchronous file writes that are not awaited were avoided, since they can reintroduce the same timing issue.

Using the Publish Return Value as a Success Signal A common approach is to rely on the return value of channel.publish() or sendToQueue(). This was rejected because the return value only indicates whether the message was accepted by the client library's local buffer. It does not confirm delivery to RabbitMQ or persistence on the broker. Publisher confirms provide the stronger guarantee required for this system.

Storing Correlation IDs in the Message Body Embedding correlation IDs in the payload was rejected because it mixes tracing metadata with business data. Consumers interested only in request tracking would need to parse the entire payload, and message schemas would be unnecessarily coupled to tracing requirements.

Using Default Guest Credentials RabbitMQ's default guest/guest account is restricted to loopback access by default. This causes problems when accessing the management API from outside the container network. Creating a dedicated user avoids these restrictions and works reliably in both development and testing environments.

Skipping Durability Although this project is an assignment, queue durability is central to the reliability guarantees being demonstrated. Without durability, broker restarts can silently remove queues and messages, making accepted orders effectively meaningless.

##Consequences

Publisher confirms introduce additional latency because each request waits for confirmation from RabbitMQ before the API returns 202 Accepted. This slightly reduces throughput but ensures that accepted requests have actually reached the broker. Using prefetch(1) limits throughput to a single in-flight message per consumer. This reduces parallelism but minimizes the number of unacknowledged messages that could be affected by consumer failures. If consumers are unavailable for an extended period, messages accumulate in the queue. This is acceptable for the scope of the assignment, although no queue limits, TTL policies, or dead-letter queues are currently configured. Multiple consumer instances can process the queue safely as competing consumers, with RabbitMQ distributing messages between them. However, concurrent writes to the same received.jsonl file are not coordinated and could create issues if several consumers share the same file. Finally, the implementation does not enforce message size limits. Extremely large payloads would be accepted, parsed, and written to disk, potentially reducing throughput and increasing memory usage.
