## Context

The producer accepts orders over HTTP and hands them to a RabbitMQ broker that this service does not control the uptime of. Four separate decisions determine whether an order survives that hand-off, and each one has a naive alternative that passes every test except the one built to catch it.

Durable queue. A queue declared without durable: true behaves identically to a durable one right up until the broker restarts. I declared the queue as durable: true in both connectProducerChannel and connectConsumerChannel — same name, same flag, both sides — and confirmed it matters by running:

docker restart pa2-rabbitmq

against a queue I had briefly declared non-durable during development. [Fill in: what you actually saw — did the queue itself disappear from the management UI, did in-flight messages vanish, what did docker compose logs rabbitmq show at the moment of restart?]

Publisher confirms. POST /publish cannot return 202 until the broker has actually acknowledged the message — a plain channel.publish() followed immediately by 202 looks correct and passes every test except demonstration (c). I ran 04-publisher-confirms-prevents-loss.test.ts publishing a batch of [N] messages with X-Publish-Mode: fire-and-forget, then docker restart pa2-rabbitmq mid-flight. [Fill in: how many of the N messages survived — 0, some, or did it vary between runs? This is the central data point of the whole ADR; don't skip it.] The same batch sent in the default confirmed mode, followed by the same restart, lost nothing.

Manual ack. The consumer acks a message only after appendFile('data/received.jsonl', ...) resolves, never before. Acking first and writing second means a consumer crash between the two loses a message the broker believes was delivered — RabbitMQ has already dropped it from the queue on ack, and nothing else has a copy. I placed the ack as the last line of handleMessage, after the await appendFile(...) call, not before.

correlationId propagation. The requirement is not "the string appears somewhere in the log" — it is a specific value carried through a specific hop: X-Correlation-Id header (or a generated UUID if absent) → msg.properties.correlationId on the AMQP message → the correlationId field written into each line of received.jsonl. I used the AMQP message's correlationId property for this, not the JSON body, since the body is arbitrary caller-supplied data and validating a protocol-level property is a different and more trustworthy guarantee than trusting a field the caller could have shaped any way they liked.

## Decision

connectProducerChannel creates a ConfirmChannel (not a plain Channel) via connection.createConfirmChannel() and asserts the queue with { durable: true }. The ConfirmChannel is a prerequisite for publishMessage's confirm callback, not a separate choice.
connectConsumerChannel creates a plain Channel and asserts the same queue name with { durable: true }. Both sides must declare identical arguments or assertQueue throws on a mismatch.
publishMessage, default path: calls channel.publish(...) with { persistent: true, correlationId } and resolves the returned Promise only inside the confirm callback — reject on err, resolve otherwise. The route handler awaits this before responding 202.
publishMessage, fire-and-forget path (only reachable via X-Publish-Mode: fire-and-forget, which exists solely for demonstration (c)): calls channel.publish(...) with no persistent flag and no confirm callback, and returns immediately without waiting on broker acknowledgment.
handleMessage parses the message body, builds a record that merges the body with correlationId: msg.properties.correlationId, awaits appendFile to data/received.jsonl, and only then calls channel.ack(msg).
X-Correlation-Id, if supplied, is validated before use — [state your actual validation: what format did you check, and what happens on a malformed header? Confirm this matches the 400 behavior the public tests check for.] — and a UUID is generated when the header is absent.

## Alternatives considered

Trusting channel.publish()'s return value as backpressure, treated as delivery confirmation. channel.publish() returns a synchronous boolean indicating whether amqplib's internal write buffer is under its high-water mark — it says nothing about whether the broker received, routed, or persisted the message. Code that checks this return value and responds 202 on true looks reasonable and will pass every test except the one built specifically to catch it, because the return value and "the broker has it" are uncorrelated most of the time. This is the naive-but-plausible version the fire-and-forget branch demonstrates the cost of.

Acking before writing to received.jsonl. Rejected because a consumer crash between the ack and the write would leave the broker convinced the message was delivered while the write never happened, losing the message with no signal that anything went wrong.

Reading correlationId from the message body instead of the AMQP correlationId property. Rejected because the body is caller-defined JSON with no guaranteed shape — using a body field means trusting whatever the client happened to send, rather than a value carried at the protocol level that the producer itself set from a validated header or a generated UUID.

Leaving RabbitMQ on guest/guest. [State what you actually configured in docker-compose.yml and why — guest is loopback-only by default, which breaks the management-API calls demonstration (b) makes from outside the container.]

## Consequences

Durability, confirms, and manual ack together mean a message is only considered "delivered" once it has been durably appended to received.jsonl — the cost is latency: POST /publish now blocks on a broker round-trip instead of returning immediately, and a slow or partitioned broker slows every caller.

If the consumer falls behind — say, appendFile starts blocking on a slow disk — messages accumulate in the queue rather than being dropped, since nothing here caps queue depth or applies backpressure to the producer beyond the confirm round-trip itself. An hour of consumer downtime with steady publish traffic means an hour's worth of messages sitting in RabbitMQ, consuming broker memory and (since the queue is durable) disk.

Running two consumer instances against the same queue is safe for throughput — RabbitMQ round-robins deliveries between them — but gives up any ordering guarantee across the two; two orders published back-to-back could be processed out of order if they land on different consumers.

Nothing here enforces a message-size ceiling, so an unusually large request body would be accepted, published, and written to received.jsonl as-is, which could stall the AMQP connection or bloat the JSONL file for no benefit — this would be worth adding size validation for in a real system.

If RabbitMQ's disk fills, durable/persistent publishes will start blocking or erroring outright rather than silently succeeding, since the broker cannot fsync what it can't write — which is the intended failure mode given the durability guarantee this ADR chose, but it does mean disk exhaustion becomes a hard outage for POST /publish rather than a degraded one.
