# ADR-003 — Translate each source with explicit field mapping, enrich from the pricing API, and filter by construction

**Status:** accepted
**Date:** 2026-10-12

## Context

Three systems send the same logical order in three shapes: nested JSON (web), flat JSON with abbreviated fields (mobile), and EDI-style XML (B2B). The canonical schema is fixed and has `additionalProperties: false`, so any stray field fails validation.

- **Encoding:** the B2B file declares `encoding="windows-1257"`. Read as UTF-8, the Latvian diacritics are silently corrupted with no error. I read the file as raw bytes and decode it with `TextDecoder("windows-1257")` before parsing.
- **Format differences:** mobile sends an epoch in seconds, a numeric currency code (978), an integer status, and one comma-separated address string. B2B sends attributes (prefixed `@_` by fast-xml-parser), a quantity as a string, and a single `<LineItem>` becomes an object while several become an array.
- **Product ids:** three formats (`PROD-001`, `001`, `SKU-PROD-001`) that must all become `PROD-XXX` before calling the pricing API.
- **Prices:** none of the sources has a trustworthy price. The B2B file has a decorative `<UnitListPrice>` in comma-decimal style. The real price must come from the pricing API, which can answer 404 (unknown product), 401, 500, or not answer at all.
- **Payment data:** web carries `customer.payment`, mobile carries `pm`/`pan`/`pexp`, B2B carries a `PaymentDetails` element under `BuyerParty`. The canonical schema has no place for any of it.

## Decision

Each of `translateWeb`, `translateMobile` and `translateB2B` reads its own format, builds the canonical customer and order field by field, calls `enrichItems`, and returns `{ order, warnings }`.

- **Filter by construction:** I never copy or delete payment fields. I only read the fields I name, so `payment`, `pan`, `PaymentDetails` and any unknown XML element are ignored. This also covers elements I have never seen.
- **Prices:** `enrichFromPricing` calls `GET /pricing/:id` with the `X-API-Key` header and formats the API's number with `toDecimalAmount`, which is `toFixed(2)`. 4.5 becomes `"4.50"`, and `unitPrice` is always a string. `UnitListPrice` is never read.
- **Failures:** a 404 returns `unknown_product` and any other non-2xx or network error returns `error`. Neither throws and neither invents a price (no fallback to 0). `enrichItems` turns them into `UNKNOWN_PRODUCT` or `PRICING_API_ERROR` warnings, and one bad line does not stop the others. A failed line item is dropped from the order. If every line fails, `order` is `null`.
- **Quantity and name** come from the source line, not from the pricing API.
- **Dates:** every `orderDate` goes through `new Date(x).toISOString()`, so all three sources produce identical strings.
- **Unrecognised values:** an unknown mobile status or B2B status becomes `"new"`, and an unknown currency code is passed through as a string.

## Alternatives considered

- **Delete payment fields from a copy of the source:** rejected. It is one forgotten field away from a leak, and it would not cover an element a source adds later. Allow-listing fields is safer.
- **Fail the whole order when one item cannot be priced:** rejected, because one unknown product would block the rest of the order. The cost is described below.
- **Integer cents instead of a decimal string:** the schema fixes `unitPrice` as a decimal string, so this was not available. Formatting once with `toFixed(2)` avoids repeated float conversions.
- **Hand-written XML parser:** rejected. `fast-xml-parser` handles the structure, and my work is mapping its output correctly.
- **Throwing on an unknown status or currency:** rejected for tolerance, but see Consequences, because this choice has a real downside.

## Consequences

- **Easier:** a new payment field or an extra XML element changes nothing, because only named fields are read. The three outputs are identical modulo ids and `receivedAt`, which the structural test checks.
- **Costs I accepted:**
  - A dropped line item means the order silently has fewer items, and any total computed downstream will be wrong. The warning is the only trace, so a caller who ignores `warnings` will not notice.
  - Defaulting unknown statuses to `"new"` can hide bad data. A wrong but valid-looking status is worse than an error.
  - Passing an unknown currency code through as a string may fail schema validation later.
  - `toFixed(2)` trusts that the API sends a number with at most two meaningful decimals. I do not handle a price with more precision.
  - Pricing is called once per line item with no caching, so an order with many items makes many calls.
- **What breaks first:** if the canonical schema gains a required field, all three translators fail validation until updated, because each builds the object by hand. A fourth source with a new product id format would need a new branch in `normalizeProductId`, and an unrecognised id would produce an `UNKNOWN_PRODUCT` warning.
- **If this model had to outlive the course:** I would return an explicit "partial order" status instead of silently dropping items, reject unknown statuses instead of defaulting them, and share one validated mapping layer instead of three hand-built objects.
