# ADR-006 — Run the checkout saga on Temporal instead of a hand-rolled orchestrator

**Status:** accepted
**Date:** 2026-11-09

## Context

In PA6 my orchestrator (pa6/orchestrator/src/server.ts) kept the saga's state itself. Before running the steps it wrote an in_progress record to idempotency-store.json, and it only wrote the final result and the step trace in finalize(), after the saga ended. If the process is killed mid-saga (for example with docker kill while shipping is slow), the record stays in_progress and there is no record of which steps completed. The next request with the same Idempotency-Key hits the in_progress branch and gets 409 idempotency_conflict, and it will keep getting it, because nothing ever finishes the saga. Nobody can tell whether the customer was charged, and nothing releases the inventory or refunds the payment. That is the problem this assignment solves.

In the PA7 crash demo I slowed shipping to 2000 ms, started a checkout with the key crash-3 and ran docker kill pa7-worker followed by docker start pa7-worker one second later. The request still returned 200 completed with all four steps, and the shipping step took 15540 ms instead of about 2000 ms, which is the time Temporal waited for the killed attempt to time out before resuming on the restarted worker. The mock logs show one payment authorize for that run and two shipping create calls (21:58:08 and 21:58:12), so the call that was in flight when the worker died ran again.

Porting to Temporal raised two decisions I did not have in PA6. First, which failures may be retried: a declined payment (4xx) will be declined again, while a 5xx or a missing answer may work next time. Second, the workflow sandbox forbids I/O, so every HTTP call had to move out of the saga code into an activity.

## Decision

The workflow (worker/src/workflows/checkout.ts) only decides the order of the steps and what to undo. It does no I/O. The six HTTP calls live in worker/src/activities/index.ts, one activity per call, and the workflow reaches them through proxyActivities.

An activity decides whether a failure is permanent from the status code. A 4xx throws ApplicationFailure.nonRetryable with the mock's own code. A 5xx or no answer throws a retryable failure. A slow call throws nothing: Temporal fails the attempt itself when startToCloseTimeout (2500 ms) runs out.

The retry policy is 3 attempts, a 200 ms first interval and a backoff coefficient of 2. A call that keeps timing out costs about 8 seconds (2.5 s, 0.2 s, 2.5 s, 0.4 s, 2.5 s) before the workflow sees it fail. That is short enough for an HTTP request to wait for, and long enough to get through a brief outage.

Compensation is plain code in the workflow. If inventory, shipping or notification fails for good, the workflow releases the inventory (only if it was reserved) and then refunds the payment, newest first. Shipping and notification have nothing to undo. If a compensation step fails, the result is failed with code compensation_failed. As in PA6, a failed inventory release does not stop the refund. The workflow never throws: every outcome is returned as a CheckoutResult, and the api turns it into the HTTP response.

The amount is summed in whole cents from the unitPrice strings and formatted as a two-digit decimal string. I ported PA6's toCents and formatCents, so no floating point is involved.

## Alternatives considered

Keep the PA6 orchestrator and add a recovery job that finishes stuck sagas on startup. This is a real option. It would need a durable record written before and after every step (today only in_progress and the final result are written), a scan of unfinished records on startup, a rule for which step to resume from, and protection against two instances resuming the same saga. That is a small workflow engine written by hand, and I would have to test its crash behaviour myself. I rejected it because Temporal already does this and is built and tested for it.

Retry every failure and let compensation sort it out. I rejected this because a declined payment would be asked three times and would delay the answer for nothing. A business refusal will not change.

One activity for the whole saga. I rejected this because Temporal could then no longer see the individual steps. After a crash it would re-run the whole saga, including the payment.

A BPMN engine such as Camunda or Flowable. I rejected it because the saga is short and code-shaped, and workflow-as-code is easier to read, test and keep next to the rest of the TypeScript.

## Consequences

Easier: a crash no longer loses the saga. The worker can be killed and restarted, and the workflow continues from the step it was on. Every attempt and every error is visible in the Temporal UI, which PA6 never had.

Harder: activities run at least once, not exactly once. If the worker dies while a call is in flight, that call may already have reached the service, and Temporal cannot know that, so after the attempt times out it runs the activity again. No engine can make this exactly once, because the failure happens between the call and the acknowledgement. For shipping this is tolerable. If authorizePayment were the step that ran twice, the customer could be charged twice. I would prevent that by sending an idempotency key to the payment provider, so a repeated authorisation is recognised as the same one.

Another cost: running workflows are replayed against the code. If I deploy a changed workflow while old ones are in flight, a change in the order of steps can make a replay fail. I would need versioning (patching) or to let the old workflows finish first.

Finally, I now have to run and watch more things: a Temporal server, a worker and the UI. If Temporal is down, no checkout can start. PA6 had fewer processes to operate.

## What the engine took over

- Remembering which steps had completed: PA6 tracked this in a completedCount variable inside the request handler in server.ts, and used it to decide what to compensate (completedCount >= 2 meant release the inventory, completedCount >= 1 meant refund). It lived only in memory, so a crash lost it. In PA7 Temporal records every step's result in the workflow history, and a restarted worker resumes from that history.
- Timeouts: PA6 wrapped every downstream call in callDownstream with an AbortController and a setTimeout of requestTimeoutMs, and turned the abort into the code "timeout" by hand. In PA7 the activity's startToCloseTimeout does it, and the workflow sees a TimeoutFailure.
- The in-progress record and saga persistence: PA6 wrote an in_progress record before the saga and the final state and trace in finalize(), using readJsonFile and writeJsonFile on JSON files. If the process died in between, the record was stuck. In PA7 the workflow history is the durable record, and the api's JSON files are only an audit mirror.
- Idempotency: PA6 kept an idempotency store (idempotency-store.json) and compared request hashes in the handler to return 409 idempotency_payload_mismatch, 409 idempotency_conflict or the stored result. In PA7 the api starts the workflow with the Idempotency-Key as the workflow id and stores a hash of the body in the memo, and Temporal refuses a second workflow with the same id. None of that comparison logic is in my worker code.
