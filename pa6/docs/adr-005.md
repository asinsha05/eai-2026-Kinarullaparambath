# ADR-005: Contract-first checkout API and a hand-rolled saga

**Status:** accepted
**Date:** 2026-11-02

## Context

POST /checkout has to turn one canonical order into four downstream calls (payment, inventory, shipping, notification) that cannot share a transaction. The hard parts were the ones the README only hints at. The canonical order carries no amount, so the orchestrator must derive it, and summing unit prices as floats gives wrong strings such as 63.9 instead of "63.90". Shipping and notification have no compensating endpoint on the mocks, so a late failure can only roll back inventory and payment. A second request with the same Idempotency-Key can arrive while the first is still mid-saga, and it needs its own answer (409 idempotency_conflict), not a hang or a second payment. A timeout (504) also had to be told apart from a business failure (422), although both leave the saga in the same half-finished state.

## Decision

The contract came first: openapi.yaml was committed and linted clean before any change to orchestrator/src/. It restates the canonical order and bounds the items array at 50, and the code enforces the same MAX_ITEMS = 50 and returns a 400 validation error above it, because the canonical schema has no bound of its own.

The saga is one sequential handler in server.ts. callDownstream makes each call with REQUEST_TIMEOUT_MS and appends a trace entry (success, failed or timeout) whether the call worked or not. computeAmount uses toCents and formatCents: prices are parsed into whole cents as integers, summed, and formatted once at the end as a two-digit decimal string. Steps run strictly one after another. On a failure or timeout, the completed steps are compensated in reverse (inventory_release, then payment_refund); shipping and notification have nothing to compensate. A failed compensation gives 422 failed with compensation_failed. A timeout maps to 504, a business failure to 422, and the status is "compensated" only if the rollback succeeded.

Idempotency is keyed on the Idempotency-Key header. The handler writes an in_progress record to /data/idempotency-store.json before the first downstream call, and finalize() overwrites it with the final status and body, so a replay returns the stored result and does not call payment again. The payload is compared through stableHash/stableStringify, so key order in the JSON does not change the hash. A different payload under the same key gives 409 idempotency_payload_mismatch, and a request that finds an in_progress record gives 409 idempotency_conflict. Both stores live in /data, so a container restart does not lose them.

## Alternatives considered

Calling the downstream services in parallel would be faster, but compensation order would become unclear, and the task requires strict sequencing that the tests check by timestamp. Returning a "pending" 202 and finishing the saga asynchronously would avoid long requests but would break the contract the tests check (one HTTP status per outcome). Choreography, as in PA5, where each service reacts to an order event on its own, was the real alternative. It needs no central orchestrator, but nobody owns the "undo everything in reverse" logic, and there is no single trace of one checkout. Rolling back after a late failure is exactly what checkout needs, so I chose orchestration. The cost is that the orchestrator knows every step and has to be changed whenever a step is added. The mocks cannot be modified, so shipping and notification could not get compensating endpoints. A late failure there therefore leaves the shipment or the notification in place, and only money and stock are rolled back.

## Consequences

Easier: one place shows the whole flow, the trace explains any outcome, and replays are cheap and safe. Harder: adding a fifth step means a new callDownstream call and a new entry in the compensation list in the right order. What breaks first: if the orchestrator is killed mid-saga it leaves an in_progress record behind, and I wrote no code to recover it. Every later request with that key gets 409 idempotency_conflict, permanently, and the store has to be fixed by hand. I accepted this cost to keep the idempotency logic simple, and a real system would need an expiry or a recovery sweep for stale in_progress records. Two requests for the same orderId with different keys are not detected as duplicates, because only the key is checked, so the same order could be charged twice. The 504 path depends on REQUEST_TIMEOUT_MS being larger than the slowest healthy mock, and a refund that is slow but not failed is treated as a failure.
