# ADR-004 — Header correlation id, file-backed dedup, classify before retry

**Status:** accepted
**Date:** 2026-10-23

## Context

Four decisions were open. Each one showed itself in my own run.

**Where the id lives.** AMQP has properties.correlationId and a headers map. The body was ruled out because the canonical schema has additionalProperties: false. My first order returned `991f170b-01c1-4462-aab7-1062f09d568a`. The same id appeared in the payment and notification logs.

**How many attempts.** I set PAYMENT_FAIL_RATE=100 and posted that order. The payment log showed "Retry (attempt 1)", "Retry (attempt 2)", then "DLQ after 3 attempts". Each line said "Payment provider unavailable (simulated)".

**What is permanent.** I published `{ not json` to orders.exchange with correlationId test1. Notification logged "INVALID (no retry): Expected property name or '}' in JSON at position 2". It made one attempt and did not retry.

**Dedup.** Notification logged "Processing 2290f99e-... (attempt 1)" and "Done". The same id arrived again and the log said "duplicate skipped 2290f99e-...". notification.log had 5 lines at the end of my run. A later start printed "3 ids already processed".

Until inventory-service was built, the suite stopped with "consumer for inventory.queue never registered within 60s" and skipped 10 tests.

## Decision

**correlationId** is a header. order-service sets it once with crypto.randomUUID() and each consumer copies it onto its result event. getRetryCount and withoutRetryHistory already work on properties.headers, so one map carries everything.

**Three attempts.** MAX_RETRIES is read with ?? "3", so a configured 0 stays 0. The simulated failures are independent per attempt, so quick retries ride out a blip.

**Permanent** means three cases. They are a SyntaxError from JSON.parse (inside the try), a missing correlationId header, and JSON that is not an object. Each goes to orders.invalid.exchange with its original bytes and headers, then is acked. Without an id a message cannot be traced or deduplicated, and a retry fixes neither.

**Dedup is a file.** notification-service loads /data/processed-ids.json into a Set at startup. It checks the id before any work. On a hit it acks and leaves notification.log alone. Writes go to a temp file and are renamed.

**Replay.** POST /dlq/replay reads with channel.get. It republishes the original bytes to orders.return.exchange with originQueue as the routing key. It strips x-death with withoutRetryHistory and acks afterwards. The response was `{"replayed":1}`. Order `991f170b` then ran as "attempt 1" and logged "Done". The retry count had reset.

## Alternatives considered

**In-memory Set.** It passes the visible test because nothing restarts mid-test. After a restart the Set is empty. A redelivered order would then be notified twice, with no trace of why. I rejected it.

**Native properties.correlationId.** It works on the wire. It gives two places to read the id, and the helpers read headers.

**Retrying everything.** It needs one catch branch. A malformed body then fails three times, lands in the DLQ, and fails again when replayed.

**Replaying through orders.exchange.** The fanout would give the order to payment and inventory again, so inventory would process it twice.

## Consequences

**Easier.** One order can be followed across three services by its id. A bad body cannot crash a consumer.

**Costs I accepted.** Notification appends the log line before it saves the id. A crash between the two logs a redelivered order twice, so the guarantee is at-least-once. The file is rewritten whole for each order and never pruned. It assumes one instance, because two replicas would each hold their own copy.

**Misclassification costs both ways.** Suppose a producer bug drops the header and I fix it later. Those messages sit in orders.invalid, which has no replay, so recovery is manual. A permanent failure treated as temporary costs three wasted attempts and a noisy DLQ.

**Replay is not fully safe.** If the cause persists, the message fails three more times and returns to the DLQ. The ack follows the republish without publisher confirms, so a crash between them delivers it twice. Payment and inventory have no duplicate check, so they could process it twice.

**What breaks first.** A future consumer that forwards a message without the correlationId header loses tracing. Its forwarded messages then go to the invalid channel. If payment succeeds while inventory stays down for more than three attempts, the order waits in the DLQ and nobody is told. Only someone watching the DLQ sees it.
