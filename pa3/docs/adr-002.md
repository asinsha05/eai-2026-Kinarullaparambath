# ADR-002 — Correlation, idle timeout and deduplication in the split/route/aggregate pipeline

**Status:** accepted
**Date:** 2026-10-05

## Context

Once the splitter runs, one order becomes N independent messages on three queues. They are processed at different speeds, possibly out of order, and possibly redelivered. The aggregator has to rebuild the order from that and must never hang if a destination stays silent. Four things were genuinely open: how correlation survives the split, which timeout number to run in production, what a partial result carries, and what makes a duplicate harmless. A fifth appeared in the router: what to do with an item type that has no route.

## Decision

- **Correlation.** `route_order` sets `correlationId = orderId` itself rather than copying it from the incoming message, so the two cannot disagree. It computes `totalItems = len(items)` once, before the loop, so every item message of an order carries the same value, even an item that ends up unroutable. Workers echo `orderId`, `itemIndex` and `totalItems` back, and the aggregator groups on `orderId`. If a worker dropped or renamed `itemIndex`, deduplication and missing-item reporting would break. If it dropped `orderId`, the result could not be attributed to any order. The aggregator drops results it cannot parse or that have an out-of-range `itemIndex`, logs them, and acks them so they cannot jam the queue.
- **Idle timeout.** `in_flight[orderId]` holds `total`, a `results` dict and a `last` timestamp (monotonic clock). `aggregate_result` refreshes `last` on every result for that order. `sweep_timeouts` runs every second and emits a partial for any order idle longer than `AGGREGATOR_IDLE_TIMEOUT_SECONDS`. That is 5 s in the test compose file. My production value would be 30 s, as a starting point to tune and not a measured number. The decision is about the gap between consecutive results of one order, not the latency of the whole order. With `prefetch_count=1` each worker handles one item at a time, so the gap is bounded by the slowest single item plus queueing delay. The digital worker takes 0.1 to 0.5 s per item, and the physical worker takes <<physical range from inventory-worker/app.py>>. I would pick the p99 of the observed inter-result gap, then multiply by about 3 to 5 for slow-start and broker hiccups. A false partial triggers retries of work that was merely slow, so it is more expensive than a late partial. I would also alert on partial rate so that "partial" keeps meaning something. A fixed deadline from the order's start would be wrong for large orders. A 50-item digital order needs roughly 15 s of sequential processing at 0.3 s average per item, so a fixed 5 s deadline would cut off a healthy order. The idle timeout lets it run as long as results keep arriving.
- **Partial contents.** A partial message has `status: "partial"`, `receivedItems`, the collected `itemResults`, and `missingItemIndexes = sorted(set(range(total)) - set(results))`. A consumer of `orders.complete` can retry or refund exactly those items instead of re-running the whole order. "Not complete" alone would force it to do that.
- **Duplicates.** `results` is a dict keyed by `itemIndex`, so a redelivered result finds its key already present and is a no-op, and the count is `len(results)`, not messages seen. Completion is checked inside the lock and the order is removed from `in_flight` before publishing, so the completion is emitted exactly once. A `finished` set of orderIds ensures a late result after a completion or partial does not recreate the order and produce a second completion. All state changes happen under one lock, and publishing happens after releasing it, so concurrent orders cannot corrupt each other.
- **Unknown item type.** It goes to a durable `orders.unroutable` queue and is logged. It is never silently dropped. No worker consumes that queue, so the order ends as a partial with that index in `missingItemIndexes`.

## Alternatives considered

- **Fixed deadline from order creation.** Rejected because it penalises large orders with healthy workers (the 50-item case) and has to be sized for the biggest order, which makes it useless for small ones.
- **Redis for aggregation state.** Rejected because at this scale a dict behind a lock is enough, and Redis adds a service to run and fail. It would be the right choice if the aggregator must survive restarts or run as several replicas.
- **Unknown type as a failure result on `orders.results`.** This would let the order complete immediately with a rejected item and give the consumer a faster answer. I chose the dead-letter queue because it keeps the original payload for inspection without inventing a worker-style result, at the cost of waiting for the idle timeout.
- **Counting messages instead of items.** Rejected because one redelivery would inflate the count, so an order could complete with a missing item or a phantom extra result.

## Consequences

- **Lost state on restart.** `in_flight` and `finished` are in memory. If the aggregator restarts mid-order, those orders' partial results vanish. Results already acked are lost, so the order may never complete. Fixing it would need persistent state, for example Redis or a database, or acking only after completion.
- **`finished` grows without bound.** In production I would expire entries after a retention period, for example a few times the timeout.
- **Orders that produce no results never time out.** An order enters `in_flight` only when its first result arrives. If every worker for it is down, or `items` is empty, the aggregator never learns the order exists. The fix is for the router to announce each order (with `totalItems`) to the aggregator, so it can start the idle clock at creation.
- **Router crash between publish and ack.** `orders.incoming` is redelivered and the items are published again. Workers then produce duplicate results, which the dict absorbs.
- **At 10x traffic or 500-item orders.** The first limits would be `publish_completion` opening a new connection on every call, and `prefetch_count=1` serialising each worker. I would reuse one publishing channel and raise the prefetch.
