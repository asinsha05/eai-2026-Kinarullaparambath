
# ADR-000 — Parse the legacy order export as bytes, reject malformed lines instead of throwing

**Status:** accepted
**Date:** 2026-09-18

## Context

The order export (`orders-20260901.txt`) is fixed-width and encoded in
CP1257, not UTF-8. Reading it with `readFileSync(path, "utf8")` does not
throw — it silently mangles every Latvian diacritic. "Bērziņš" comes out as
garbage (either `?` characters or replacement characters, depending on how
the bad decode happens), but the file still parses, the columns are still
the right width, and a report gets produced that looks completely normal
until someone reads a name. That is the dangerous failure mode this
assignment is built around: nothing crashes, so nothing tells you it is
wrong.

The customer master (`customers.csv`) is UTF-8 — a different encoding from
the order file, in the same integration, because the two files come from
systems built years apart.

Two other traps in the same file: amounts use a comma as the decimal
separator (`1234,56`), and line 6 of the order file is truncated to 26
characters instead of the required 77 — a record that was cut off mid-write
somewhere upstream. Neither of these announces itself either: `parseFloat`
happily reads `45,20` as `45`, and a naive line-by-line loop that doesn't
check length just throws on the short line and takes the whole run down
with it.

## Decision

`decodeOrderFile` reads the order file as raw bytes (`readFileSync` with no
encoding argument, returning a `Buffer`) and decodes it explicitly with
`new TextDecoder("windows-1257")`. The customer CSV is read separately with
`readFileSync(path, "utf8")`, because it is actually UTF-8 — the two files
are never decoded the same way.

Each line is split from the decoded text on line-ending characters so
either LF or CRLF works, and a single trailing empty entry (caused by a
final newline) is dropped without touching real content, so 1-based line
numbers for `rejected` stay accurate.

A line is only accepted if it is exactly 77 characters long. If it isn't,
`ingest` pushes it to `rejected` with its line number and the reason
"expected 77 characters, got N", and moves on to the next line instead of
throwing — one bad record does not take down the whole run.

Fields are sliced by fixed column position, never by splitting on
whitespace, because `customerName` contains spaces.

`toDecimalString` converts the comma to a period and returns a string. The
`amount` field on `Order` is typed as `string`, not `number`, everywhere —
it is never passed through `parseFloat` or `Number()` at any point, which
is what keeps `"45,20"` as `"45.20"` instead of quietly becoming `45.2`,
and what keeps negative amounts (refunds) from looking like an error to be
filtered out.

`unmatchedCustomers` is computed by taking every customer id in the CSV and
subtracting the set of customer ids seen on accepted orders — deliberately
only accepted orders, so a customer whose only order was on the truncated
line 6 still correctly shows up as unmatched.

## Alternatives considered

**Add `iconv-lite` for the decoding.** Rejected because the assignment
explicitly disallows encoding dependencies, and because it isn't needed —
`TextDecoder` supports the `"windows-1257"` label natively in Node 20+, so
pulling in a dependency for something the standard library already does
would just be extra surface area for no benefit.

**Parse each line with a regular expression instead of column slicing.**
A regex could technically extract the same six fields, but it would have to
re-encode the exact column widths as capture-group lengths anyway, so it
buys nothing over slicing by position and is harder to read at a glance
against the layout table in the README.

**Store `amount` as a `number` and format it back to a string on output.**
Rejected because the round trip through a float is exactly the failure
this assignment is testing for — `7800,00` becomes `7800` once it passes
through `Number()`, and there is no way to recover the two dropped
trailing zeros afterward. Keeping it a string end-to-end means the value
is never at risk of losing precision.

**Throw on the malformed line instead of collecting it into `rejected`.**
This is the easiest wrong answer, because it is what naive code does by
default. It is rejected because it means one bad line in a daily batch
would take down the whole morning's ingestion instead of losing exactly
one record and reporting why.

**Ask the upstream system for a JSON or API feed instead of parsing this
file at all.** This is the alternative most worth naming honestly: nobody
is going to build an API for this file, and the whole point of the
assignment is that reading the file, not requesting a better format, is
the realistic option available this week. If this integration had to run
for five years, this is the option I would actually push for — see
Consequences.

## Consequences

**Easier now:** a daily run survives a single malformed record without
manual intervention, and the rejected list gives a human something
specific and actionable to look at (line number, raw content, reason)
rather than a stack trace.

**Harder / more fragile going forward:** the column layout is hardcoded to
the widths described in this week's README. If the upstream system adds a
field in the middle of the record, shifts a column boundary, or widens
`customerName` past 32 characters, this code has no way to notice — a
longer name would simply get silently truncated, not rejected, since it
still slices cleanly. That is a real risk this design leaves open.

**What would actually change over five years:** I would push to replace
the fixed-width read with a proper contract — even something as small as
the upstream team exporting the same data as CSV with a header row would
remove the column-position fragility entirely, and a JSON/API feed would
remove the encoding guesswork too. Short of that, I would add a
schema-version marker or a checksum on the file so a silent format change
fails loudly instead of producing a plausible-looking wrong report, which
is the actual risk this decision does not protect against.
