# ADR-007 — The saga is started by the order.accepted event, and the message is acked only after the outcome is persisted and published

**Status:** accepted
**Date:** 2026-11-20

## Context

In PA6 the saga was started by an HTTP request to the orchestrator. If the orchestrator was killed mid-saga, the idempotency record stayed `in_progress`, so every retry with the same key got 409 for ever, and nobody could tell whether the customer had been charged. Intake would also have had to wait for a whole saga, or know the orchestrator's address.

## Decision

Intake publishes `order.accepted` to `orders.exchange` after a publisher confirm. The orchestrator (`orchestrator/src/server.ts`, `onMessage`) consumes `saga.queue` with prefetch = SAGA_CONCURRENCY (5). Each saga holds its message unacked until `conclude()` has written the new state and the outcome event to `saga-store.json` and published the event to `orders.outcome` with a confirm; only then does it ack. A redelivery of a saga that already has an outcome republishes the stored outcome (hop `saga.dedupe`) and runs no step. Intake learns the state by consuming `orders.outcome` through its own queue `intake.outcome` (`onOutcome` in `intake/src/server.ts`) and applies a transition table: an event that is not an allowed move from the current state is ignored, so a terminal state can never move backwards.

## Alternatives considered

- Acking on receipt: simple, but a crash before the saga finishes loses the order silently. Rejected.
- An outbox written in the same transaction as the saga state: the right answer with a database. Without one, our persist-then-publish-then-ack sequence gives the same effect through redelivery, at the price of duplicate events.
- Intake calling the orchestrator over HTTP, as in PA6: brings back the stuck idempotency record. Rejected.
- Intake polling the orchestrator for the state: more coupling and more load. Rejected for the event subscription.

## Consequences

Outcome events are at-least-once, so every consumer must tolerate duplicates (the notifier dedupes on correlationId, intake ignores illegal transitions). A crash after persisting but before publishing heals itself: the unacked message returns and the stored outcome goes out again. Prefetch = SAGA_CONCURRENCY means five sagas can run at once and the sixth waits in `saga.queue`, which is also what the lag alert measures. The cost is that `saga-store.json` is rewritten completely on every step, which will not scale, and that `intake.outcome` is an extra queue that the brief does not list.
