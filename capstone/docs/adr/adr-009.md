# ADR-009 — The trace is built from a wire tap on trace.events, not from scatter-gather or OpenTelemetry

**Status:** accepted
**Date:** 2026-11-20

## Context

An operator needs to see the whole journey of one order across intake, the orchestrator, the notifier and the mocks, even when a service has crashed since.

## Decision

Every service publishes one hop record per unit of work to the fanout `trace.events` (`emitHop` in `shared/trace.ts`). The observer consumes `trace.store`, appends each hop to `trace-store.jsonl` and keeps an in-memory index by correlationId, rebuilt from the file at start. `GET /trace/:cid` sorts by startedAt. Publishing a hop is fire-and-forget: it uses the confirm channel without waiting for the confirm and swallows errors, so a lost hop can never fail an order. A lost hop leaves a gap in the trace and nothing else. If the observer is down, the durable `trace.store` queue keeps the hops and the observer catches up on restart. A nack cannot rewrite headers, so every delivery attempt of one message has the same causationId (the publisher's hop); the attempts differ by `attempt`, read from `x-death`, and each `saga.retry` hop is caused by that attempt's consume hop.

## Alternatives considered

- Scatter-gather: ask each service for its hops at read time. A crashed service would take its history with it, and every service would need a query endpoint. Rejected.
- OpenTelemetry: heavier, and the brief forbids it as a replacement for our own header propagation.
- Confirmed, blocking hop publishing: gives a complete trace but couples every order to the broker's speed. Rejected.

## Consequences

The trace is best-effort, not an audit log. The observer dedupes on hopId, so redeliveries are harmless. The cost is that `trace-store.jsonl` grows without bound and has no retention.
